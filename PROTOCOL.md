# LibreNotes sync protocol

This document describes the wire protocol between LibreNotes clients and the
sync server, and the exact encryption envelope clients apply before anything
leaves the device. It is derived from the code (`server/lib/api.dart`,
`server/lib/db.dart`, `packages/notally_core/lib/src/`,
`clients/app/lib/sync/`), not from memory — where this document and the code
disagree, the code wins and this file is the bug. Places where the code
disagrees with `CLAUDE.md` are listed in [Known discrepancies](#known-discrepancies).

Current protocol version: **`_apiVersion = 1`**.

## Overview

One owner, many devices, one server. The server is **content-blind**: it stores
opaque ciphertext plus the plaintext sync metadata it needs (`id`, `rev`,
`seq`, `deleted`, `purged`, `updatedAt`). All cryptography is client-side. The
server is meant for a home LAN or a Tailscale/WireGuard mesh and speaks plain
HTTP — never expose it to the public internet.

There is no CRDT. Sync is a global changelog (`seq`) plus a per-note revision
(`rev`), and conflicts are resolved by the user.

## Transport and authentication

- JSON over HTTP. Request and response bodies are `application/json`.
- Binary fields (`ciphertext`, `nonce`, `wrappedDek`, `salt`) are **standard
  base64** (with padding) strings.
- Every route except `GET /health` requires `Authorization: Bearer <token>`.
  A missing or wrong token gets `401 {"error":"unauthorized"}`.
- The token is a single shared secret (one for the whole server; there are no
  per-device tokens). It comes from `NOTALLY_TOKEN`, or is generated (32 random
  bytes, base64url, no padding) and persisted to `<NOTALLY_DATA>/token`.
- The token is compared with plain string equality, not constant-time.
- Server config is environment variables: `NOTALLY_DATA` (default `data`),
  `NOTALLY_HOST` (default `0.0.0.0`), `NOTALLY_PORT` (default `8787`),
  `NOTALLY_TOKEN`.

## Version negotiation

Every response (including 401s) carries the header
`x-librenotes-api-version: <int>`.

The client checks it on `GET /health` (called once at connect via
`checkApiVersion`) and on `GET /changes`. If the header is **greater** than the
client's own `_apiVersion`, the client raises `VersionMismatchException` and
stops syncing — it needs updating. A missing or non-integer header is tolerated
(old servers). A server older than the client is **not** rejected.

`_apiVersion` must be bumped in lockstep in `server/lib/api.dart` and
`clients/app/lib/sync/sync_api.dart` whenever the wire protocol changes.

## Data model on the wire

### `EncryptedNote`

```json
{
  "id": "uuid",
  "ciphertext": "<base64: cipher || 16-byte tag>",
  "nonce": "<base64: 24 bytes>",
  "rev": 3,
  "seq": 41,
  "deleted": false,
  "purged": false,
  "updatedAt": 1700000000000
}
```

| field | meaning |
|---|---|
| `id` | UUID, generated by the client so offline creates work. |
| `rev` | Per-note revision, starts at 1, +1 on every accepted write. Plaintext. |
| `seq` | Global, server-assigned, strictly increasing change cursor. The note's `seq` is replaced on every accepted write. |
| `deleted` | Tombstone flag. Ciphertext and nonce are emptied (zero-length). |
| `purged` | Permanent delete ("empty trash"). Implies `deleted`. Clients hard-delete their local row. |
| `updatedAt` | Server clock, ms since epoch. Not the note's user-visible edit time (that lives in the ciphertext). |

`purged` is omitted-tolerant on parse (defaults to `false`).

### `ChangesResponse`

`{"notes": [EncryptedNote, ...], "latestSeq": 41}` — notes ordered by `seq`
ascending; `latestSeq` is the server's global high-water mark.

### `PushRequest`

`{"ciphertext": "<b64>", "nonce": "<b64>", "baseRev": 2}` — `baseRev` is the
`rev` the client edited from; `0` means "new note".

### `PushResult`

`{"status": "applied" | "conflict", "note": EncryptedNote}` — on `applied`,
`note` is the freshly stored version; on `conflict` (HTTP 409), `note` is the
server's current version.

### `Keystore`

```json
{
  "wrappedDek": "<b64: 24-byte nonce || ciphertext || 16-byte tag>",
  "salt": "<b64: 16 bytes>",
  "kdfMemory": 19456,
  "kdfIterations": 2,
  "kdfParallelism": 1
}
```

## Endpoints

| Method & path | Auth | Purpose |
|---|---|---|
| `GET /health` | no | Liveness; body `{"ok":true}`. Also used for version negotiation. |
| `GET /changes?since=<seq>` | yes | Pull. Returns every note (including tombstones/purges) with `seq > since`. A missing or unparsable `since` is treated as `0`. |
| `PUT /notes/<id>` | yes | Create/update. Body `PushRequest`. `200` + `PushResult(applied)` or `409` + `PushResult(conflict)`. `400 {"error":"invalid request body"}` on malformed JSON/base64. |
| `DELETE /notes/<id>?baseRev=<n>` | yes | Tombstone. Same conflict rules as `PUT`. `400` if `baseRev` is missing/non-integer. |
| `DELETE /notes/<id>/purge` | yes | Permanent delete. No conflict check. Always `200 {"ok":true}`. |
| `GET /keystore` | yes | The wrapped DEK bundle; `404 {"error":"no keystore"}` if none yet. |
| `PUT /keystore` | yes | Store/replace the bundle. `200 {"ok":true}`; `400` on malformed body. |

Unknown routes return the router's default 404.

## Sync semantics

### Revisions and conflicts (`PUT`, `DELETE`)

Each write runs in one `BEGIN IMMEDIATE` SQLite transaction.

- **Note does not exist on the server** → insert with `rev = 1`, fresh `seq`.
  `baseRev` is ignored in this case (a client re-pushing a note the server has
  lost is treated as a fresh create).
- **Exists and `existing.rev == baseRev`** → accept: `rev = baseRev + 1`, new
  `seq`, `deleted = 0`, `purged = 0`, store the new ciphertext/nonce.
- **Exists and `existing.rev != baseRev`** → **409**, nothing written, the
  response carries the server's current note. A new note pushed with
  `baseRev = 0` against an id that already exists therefore conflicts.

Consequences worth knowing:

- A `PUT` whose `baseRev` matches a *tombstoned or purged* note's `rev`
  **resurrects** it (`deleted` and `purged` reset to 0).
- `DELETE` on an id the server has never seen returns `409` with a synthetic
  tombstone (`rev: 0`, `deleted: true`, empty ciphertext) so the client can
  reconcile.
- The server never inspects ciphertext, so it cannot tell whether two writes
  are "really" different. Conflict detection is purely on `rev`.

### Pull and the cursor

The client stores the last `latestSeq` it received and sends it as `since`. A
pull never moves a note's `rev` backward, and a client's own accepted push
does **not** advance its stored cursor (its own change simply comes back on the
next pull with an equal `rev`, which the client recognises and ignores).

On pull, per returned note, the client:

1. `purged` → hard-delete the local row, regardless of local state.
2. Local row is **dirty** (unpushed edit) and `remote.rev > local.rev` → record
   a **conflict** (both versions kept; the user chooses). Equal `rev` is just
   the client's own base coming back and is left for the push phase.
3. Otherwise apply the remote version (a tombstone for a note the device never
   had is skipped).

Then it stores `latestSeq` and pushes every dirty note, skipping notes with an
open conflict. A `409` on push also becomes a conflict.

### Conflict resolution (client-side)

The user keeps either version (or, in the app, a manually merged text).
"Keep mine" re-pushes the local content with `baseRev = <server's current rev>`,
so it is accepted and wins; "keep theirs" applies the server version locally.
If the server moved again in between, the conflict is refreshed with the newer
remote.

### Deletes, trash, purge

- **Delete** → `DELETE /notes/<id>?baseRev=n`: tombstone (`deleted = 1`,
  ciphertext/nonce emptied, `rev + 1`, new `seq`). Other devices keep the
  note's text locally in their trash; only sync metadata changes.
- **Purge** → `DELETE /notes/<id>/purge`: sets `deleted = 1, purged = 1`,
  empties ciphertext, `rev + 1` (or inserts a `rev 1` purged row if the id was
  unknown), new `seq`. The pushing client keeps its row until the call
  succeeds, then hard-deletes it; if the call fails it hard-deletes anyway
  (best effort). Calling purge twice just bumps `rev` again.
- Tombstones and purge markers are **never compacted**: `GET /changes?since=0`
  returns every note ever written.

### Keystore

The first device to connect finds no keystore (`404`), wraps its existing local
DEK (see below), and `PUT`s it. Later devices `GET` it, derive the KEK from the
passphrase and the stored salt/params, and unwrap the DEK (adopting it and
re-encrypting any local notes under it). `PUT /keystore` unconditionally
replaces the previous bundle — there is no compare-and-swap.

## Encryption envelope

All of this is implemented in `clients/app/lib/sync/note_crypto.dart` and
**only** on the client.

### Keys

- **DEK** — random 256-bit key (XChaCha20-Poly1305). Encrypts every note
  payload. It also encrypts the notes' content at rest in each device's local
  database, and is stored raw in the platform keyring on each device.
- **KEK** — 256-bit key derived from the passphrase with **Argon2id**:
  - password = UTF-8 bytes of the passphrase
  - salt = 16 random bytes (stored in the keystore)
  - memory = **19456 KiB**, iterations = **2**, parallelism = **1**,
    output = 32 bytes (the defaults; the parameters actually used are stored in
    the keystore and read back on unlock)
- The KEK is derived on demand and never stored or sent.

### Wrapping the DEK

`wrappedDek = nonce(24) || ciphertext(32) || tag(16)` = 72 bytes, where
`ciphertext || tag = XChaCha20-Poly1305(key = KEK, nonce, plaintext = DEK)`
with a fresh random 24-byte nonce and **no associated data**. A wrong
passphrase fails the tag check (`SecretBoxAuthenticationError`).

### Encrypting a note

```
nonce      = 24 random bytes (fresh for every write)
plaintext  = UTF-8 JSON of the payload (below)
box        = XChaCha20-Poly1305(key = DEK, nonce, plaintext)    # no AAD
ciphertext = box.cipherText || box.tag(16)                      # what goes on the wire
```

The nonce is sent separately (`nonce`), not prefixed to `ciphertext`.

### Payload (inside the ciphertext)

```json
{
  "title": "string",
  "body": "string (markdown)",
  "pinned": false,
  "color": "#2a2a2a  or  grad:#aaaaaa,#bbbbbb[,#cccccc]",
  "createdAt": 1700000000000,
  "updatedAt": 1700000000000,
  "archived": false,
  "expiresAt": null
}
```

Everything here is invisible to the server, including archive state and
self-destruct timers. On read, missing fields default (`pinned`/`archived`
false, `color` `#2a2a2a`, `createdAt`/`updatedAt` fall back to the server's
`updatedAt`, `expiresAt` null), so older/newer clients can interoperate.
Tombstones have no payload.

## What the server can see

Despite E2EE, the server learns: note ids, how many notes exist, the revision
and write count of each, the order and timing of every write (`seq`,
`updatedAt`), which notes are deleted or purged, the approximate size of each
note (ciphertext length), the keystore's KDF parameters and salt, and the
client's IP/headers. It cannot read titles, bodies, colors, pin/archive state,
or expiry times. Anyone holding the bearer token can also overwrite the
keystore and any note.

## Known discrepancies

Found while writing this document; the code is the source of truth.

1. **Payload fields.** `CLAUDE.md` lists the payload as `{title, body, pinned,
   color, createdAt, archived}`. The app (`SyncService._payloadOf`) actually
   also sends `updatedAt` and `expiresAt`.
2. **`Note.toPayload()` is stale.** The shared `notally_core` helper emits
   `{title, body, pinned, color, createdAt, expiresAt}` — no `archived` and no
   `updatedAt`. The client does not use it for sync, so there is no bug today,
   but anything that did would drop archive state.
3. **`/health` and version.** `CLAUDE.md` says the version mismatch is driven
   by `_apiVersion`; precisely, only a *newer* server than the client is
   rejected (and an absent header is tolerated).
4. **Keystore replacement.** `PUT /keystore` has no guard: any token holder, or
   two devices connecting at the same time to a fresh server, can overwrite the
   wrapped DEK. Overwriting it with a different DEK would strand notes
   encrypted under the old one for devices that re-unlock.
5. **Resurrection.** A write with a matching `baseRev` revives a tombstoned or
   purged note (see above); `CLAUDE.md` describes purge as final.
